# 十组 HIBE×IBS 同机基本性能比较方案

> 本PR交付实验方案、十组完整配置和规划预检记录，供远端审查；尚未启动性能实验。后续按本方案在当前会话串行实施，不调用子智能体。用户本轮只要求方案与PR，不含容器制作、算法优化、报告改写或长实验执行。

**目标：** 在同一台机器、同一源码版本和相同输入下，为报告已覆盖的2种HIBE×5种IBS生成一批可比较的完整系统成本数据。

**结构：** 调度器串行执行30个独立试验，worker只调用公共装配与协议接口，汇总器校验来源后按操作分别比较。保留两个HIBE自身的缓存与委派行为，首次、同进程重复和新进程恢复分别计时。

**工具：** WSL2／Sage 10.7／Python 3.12.13，现有原生桥，`time.perf_counter()`及10 ms进程树RSS采样，JSON／CSV／静态图。规划源码为main `cb96cdb9417c5df2f3837e2668c4b9f49db726f5`；正式执行改为固定包含新runner的干净提交并重新登记指纹。

## 1. 实验对象与参数

完整数值配置及Suite摘要见[matrix.json](../../research/2026-10-21-ten-combination-benchmark-plan/matrix.json)，不是按名称在运行时重新取最新默认值。十格均使用Hybrid、BYTEAUTH、当前单写者状态策略、`allow_mock=false`和既定的`secure/true/true`声明，不另设安全准入任务。

| HIBE | 参数 |
|---|---|
| LATTE-3/COSAC-FIX | `latte/seed32`；原生32 B种子封装、86 B内层身份，既有身份预算不变 |
| Lai C2 | `lai-ideal-hibe/target-research`；n=2048、k=39、q=274877976577、p=2、l=2、sigma=2、sigma_r=1；同为32 B种子、86 B内层身份 |

| IBS列（各配两个HIBE） | 配置选择 | 编码 | Hybrid载荷上限 | 应用消息容量 |
|---|---|---|---:|---:|
| BNN/ML-DSA-44 | `cert-ml-dsa/ml-dsa-44` | reference | 65536 B | 59191 B |
| BNN/Falcon padded-512 | `cert-falcon/falcon-padded-512` | reference | 65536 B | 63106 B |
| Luo模格 | `luo-module/research` | compact | 65536 B | 3924 B |
| SRGG论文PARAM-I | `srgg2025-paper/PARAM-I`，table-standard-deviation | compact | 131072 B | 65364 B |
| Sageloli RSIS v3 PARAM-I | `sageloli-rsis/PARAM-I` | reference | 8388608 B | 3924 B |

两行中同一IBS的参数、编码、身份上限和Hybrid预算完全相同，只有HIBE及其版本绑定不同；所有胶囊上限均为4 MiB。不同IBS保持各自既有预算，因为Sageloli签名需要更大的内部载荷。预算差异公开列示，实际应用输入统一为32 B；不测各方案不同的最大容量来替代固定工作量。

A=`latte-mldsa44`、B=`latte-srgg-I-compact`、C=`lai-c2-sageloli-I`与原[三代表冻结Suite](../../deliveries/2026-10-19-report-three-selection/suites/)逐字段相同。Lai＋Luo本轮也选compact，消除旧批次reference与LATTE compact的格式差异；这是新批次配置，不改旧收据，不将旧数值填入新表。

本轮不扩展到Wang/PW、ABB、CHKP或其它参数档，也不把同算法的编码档位重复计为新算法。这里的十组是报告现有矩阵的补测范围。

## 2. 方案选择与比较范围

采用**每格各自生成3个独立完整根**。这样系统建立、发送者发钥和接收者发钥都能单独计量，各列不共享HIBE根或主密钥。

另一种方式是共享3个HIBE根再替换IBS，能够做同根配对并节约准备成本，但会改变独立单位和建立成本的含义。该方式不用于本轮主表。历史共享根试验继续保留为单独批次。

输出按系统建立、发钥、首次加密、首次解密、同进程重复、新进程恢复分别排序，并提供完整密文、密钥尺寸和内存列。排序含义为“这些固定参数和实现下的实测成本”，不合成无应用权重的一个总分，也不重新推定各原语的统一NIST等级。

## 3. 固定运行环境

- 单机：当前Intel Core i9-14900HX，Ubuntu 24.04／WSL2；已有只读探测见[planning-checks.json](../../research/2026-10-21-ten-combination-benchmark-plan/planning-checks.json)。
- 使用`~/miniconda3/envs/sage/bin/python`；Sage 10.7、Python 3.12.13、NumPy 2.4.3、cryptography 50.0.2、setuptools 82.0.1。保持Sage所配NumPy，不在计时阶段安装或升级软件。
- 同一时刻只运行1个试验worker。OMP=4，OpenBLAS=1、MKL=1、NUMEXPR=1；协调器与所有子进程固定到同一组逻辑CPU 0–3并记录实际亲和性。不能把WSL逻辑CPU号宣称为已确认的四个物理性能核。
- Linux本地文件系统存放冻结源码、运行状态和输出。Windows工作树只用于提交／导出；不从`/mnt/d`启动正式测量，也不依赖Windows格式的worktree `.git`被Linux Git直接识别。
- 预先构建LATTE、ML-DSA、Falcon与Sageloli原生桥，记录GCC／G++、GMP／MPFR／MPC／FLINT／OpenSSL版本、实际链接库／BLAS标识、编译选项、源码清单和二进制SHA-256。所有试验使用同一套已固定引擎；构建和依赖安装不计入密码操作，批次中途不得重建。
- 每个worker先完成解释器导入、原生依赖探测和`build_runtime`，再开始阶段计时。单列运行时准备与整进程wall时间；“首次操作”指新状态的首次调用，不指清空OS缓存或整机冷启动。
- 接通电源，保持同一电源模式；暂停其它密码基准、编译和重CPU任务。每个独立试验结束固定等待30秒，调度器每5秒检查中断信号。记录批次开始／结束环境和每个job时间，不宣称容器或WSL能消除硬件、负载、温度的差异。
- 正式开始前要求至少4 GiB可用内存、12 GiB空闲磁盘；当前WSL总内存约7.62 GiB。进程树RSS达到4 GiB时停止该job并保留资源失败记录；采样RSS为保守资源控制，不写成独占内存或PSS。

规划探测复用了已有原生引擎及依赖目录，十组公共预检通过，未生成密钥。现有Sage环境未发现pytest包；实现阶段先在独立测试依赖目录准备并记录pytest版本，再冻结正式环境。规划时探测的引擎摘要只能证明本次依赖可用，正式批次仍须核对与执行源码匹配的原生构建。

## 4. 输入、独立性与顺序

公开输入已写入matrix：发送者为64个ASCII `A`，接收者为64个ASCII `B`，消息为字节`00`至`1f`共32 B。它们只是相同的测试负载；密钥、签名、加密与Lai委派始终使用系统CSPRNG，不设置密钥随机种子。

每格3个独立根，每根执行：1次首次加密／解密、3对同进程重复加解密、在一个新进程中加载状态后3次解密。因此主批次共有：

| 项目 | 数量 |
|---|---:|
| 独立完整系统根、发送者发钥、接收者发钥 | 各30 |
| 首次加密、首次解密 | 各30 |
| 同进程重复加密、重复解密 | 各90 |
| 新进程状态恢复 | 30 |
| 恢复后解密 | 90 |
| 实际加密／解密总调用 | 120／210 |

每个“恢复”进程先加载一次，再解密3次；不能将其计为3次独立新进程恢复。9个重复操作仍来自3个独立根，不能写为9个独立样本。

分3轮执行，每轮包含十格各1个新根。使用独立的`random.Random(20261021)`只打乱每轮调度顺序，不影响密码随机源；执行前将30个job的完整顺序、输入摘要及Suite摘要写入批次清单并占位。校准试验不进入正式30个job，也不复用其根。

## 5. 每个job的阶段与计时边界

### 5.1 生成进程

1. 在新解释器加载指定完整Suite，核对源码、引擎、环境指纹，公共预检及容量检查必须通过。
2. 计时`protocol.setup`、`skgen`、`rkgen`，分别记录系统建立、发送者发钥和一级接收者发钥。
3. 计时`encrypt(...).to_bytes()`，包括签名、所选包装、完整wire编码和原生子进程；记录实际wire长度。
4. 计时公共`decrypt`接收该wire的全过程，包括严格解码、认证、HIBE及IBS检查和需要的委派；结果逐字节等于32 B原文才通过。原生阶段计时是总计时的子项，不能再次相加。
5. 将首个有效密文、公共对象、发送者／接收者对象及主状态保存到私有目录。持久化另计时，不混入密码操作；按现有公共接口进行规范序列化。
6. 在同一进程执行3对重复加解密，每次加密取新随机并产生新密文，每次解密检查原文。记录内部采样计划和证书缓存的实际调用次数；不调用额外的协议接收会话准备接口。
7. 测量外执行截断1 B和篡改1 bit两项外层拒绝检查，结果必须为失败；这些调用单独记账，不计入上表120／210次诚实操作，也不写入性能分布。其它已有功能负例不在本轮全部重跑。

### 5.2 新进程恢复

恢复进程只接收已保存的公共对象、接收者对象、首个密文和输入摘要；不打开主密钥或发送者私钥。加载、规范解析和接收钥校验单列为`restore-objects`，随后解密3次。

| HIBE | 恢复／重复解密的实际要求 |
|---|---|
| LATTE | 保留既有持久化身份缓存语义。恢复后不生成新根、不签名、不重新发钥，熵读取及原生调用按现有缓存恢复契约检查 |
| Lai C2 | 每次正常解密执行1次真实未缓存Derive，允许并记录新采样熵，单列`derive_seconds`和调用数；不得改为零熵恢复或偷偷复用prepared leaf |

两组恢复都检查原持久文件摘要不变。不能因为Lai需要随机委派而给它套上现有LATTE专用的“禁止全部熵读取”断言。观测wrapper只能透传公共调用并记录时间／计数，不读私有矩阵或修改返回值、随机源、采样与缓存策略。

本轮主表记录后端既有默认行为。Lai接收会话准备及其约28.6秒的准备后解密属于已有优化消融，不替代本表约7～11分钟的完整解密；其它已合入内部优化保持当前版本，不在本轮增加开关对照。

## 6. 统计与结果形式

- 首次操作分别保留3根的原始值及中位数、最小／最大值。
- 同进程重复及恢复后解密：先求每根3次操作的中位数，再对3个根中位数取中位数；同时保留全部9次观测及其根标识。
- 3根仅支撑小样本工程比较。展示三个根的点和范围，不生成貌似稳定的尾概率、总体失败率或95%置信区间。
- 对每一操作分别给出2×5表；另列公钥、主密钥、发送／接收钥、实际密文的字节数及范围。主密钥只公开尺寸和摘要统计，不公开其字节或内容。
- 内存复用`runtime_metrics.measured_phase`的10 ms自进程／进程树RSS采样。内核`ru_maxrss`只作为累计高水位，不能作为各阶段独立峰值；共享页重复计入、短峰可能遗漏的口径保留。
- 主表列出编码、载荷预算、应用输入和源版本。不同IBS的实际签名与密文长度是组合成本的一部分；按同一IBS比较HIBE时保持该列参数和预算相同。
- 只合并本批次中通过来源与完整性核对的样本。历史Ultra 9、Xeon和原i9数据放在参考区，不补齐本轮空格。
- 输出`environment.json`、`batch-manifest.json`、逐job公开收据、`measurements.csv`、`summary.json`、各阶段耗时图及尺寸图、失败／超时表和只读复核入口。

## 7. 超时、失败与续跑

固定上限写入批次清单：单阶段1800秒，生成及重复进程7200秒，恢复进程5400秒，正式批次总wall预算36小时（包含每个job后的30秒间隔）；依赖构建与校准另计。不得在看到慢样本后静默放宽上限。

job以排他创建的文件从`pending`进入`running`，阶段结束后原子写入记录；成功才进入`passed`。超时、资源不足、熵／调用契约不符、明文不符分别记为明确失败状态。先终止该worker的进程组，保留诊断与已有记录，不能停止无关进程。

续跑先检查执行源码、全部配置、引擎及软件指纹与批次清单一致。已完成job核对摘要后跳过；尚未开始的job按原顺序继续。如果生成进程完整通过而恢复进程尚未启动，可直接从原私有文件开始恢复。已启动但中断或失败的阶段不自动重试、不重新抽根替换失败样本；补测另编号并与原失败记录同时保留。

某格不足3个完整通过根时展示计划／成功／失败数和已有观测，不填0、不用旧数据补格，不宣称十组完整性能矩阵已完成。来源改变或36小时预算耗尽时停止整批并输出部分结果。此处的资源上限是实验执行限制，不改变原算法参数。

私有文件写入`~/.cache/ibme-bench/ten-combinations-20261021-01/private/`，目录0700、文件0600；公开记录仅允许环境、配置、长度、时间、结果和源码指纹等字段。异常栈、原生stdout、密钥和随机内容保存在私有区，不装入新的支撑材料。
